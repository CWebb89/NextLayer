# The two projects: verified status

An engineering status of `next-layer` and `HFW` as a pair, checked against the code
on **2026-11-17** — not against earlier notes. Every line below was confirmed by
reading a file, running a generator, or running a command; where that was not done it
says so.

Verified at: next-layer `65437eb` (clean tree), HFW `c95e24d` (clean tree).

Read `rust-engine-plan.md` for the plan this status serves, `engine-boundary.md` for
the generated measurement, and `features.md` for the per-setting ledger.

## The shape of it

Two repositories, one product. **next-layer** is the application (C++/Qt/QML, 26.5k
lines): plate, presets, painting, calibration, preview, printer connection, project
files. **HFW** is the engine (Rust, 32k lines, 12 crates): mesh, geometry, layers,
walls, infill, supports, toolpaths, G-code, verification. They stay separate
repositories; the boundary is a versioned interface, not a merge.

A third tree exists inside next-layer and is neither project:
`next-layer/upstream/` is a restructured PrusaSlicer (605,785 lines, its own git
repository, pinned at `30ef5919`), and it is what `rust-engine-plan.md` exists to
retire. Today next-layer still links it for the plate model, settings, arrange,
preview data and project files, while slicing already runs on HFW.

## Where next-layer stands

Built, slices through HFW behind `NEXT_LAYER_ENGINE=hfw`, and prints on one machine:
a Voron 2.4 R2 350 over Klipper/Moonraker. Two real prints recorded
(`docs/real-prints.md`), both produced by the old engine.

43 of 76 files under `src/` reach into the C++ engine. `engine-boundary.md` lists
them, sorted by the phase that retires them, and `tools/check` now fails when that
document goes stale.

## Confirmed open, in the order the handoff ranks them

**0. The G-code the app produces carries a Prusa COREONE start sequence, not the
Voron's.** Found 2026-11-17 while checking a file for printing. `--dump-config` shows
`start_gcode` = the COREONE block (`M862.3 P "COREONE"`, `M555`, `G29` mesh, park at
`X242 Y211`) and `end_gcode` = its Prusa counterpart, while `printer_model` and
`max_print_height` in the same file are the Voron's. The selected printer preset
(`presets/local/next-layer-custom/Custom/preset-printer-voron-2-4-350-0-4-nozzle-copy.yaml`)
has its own three-line `start_gcode` (`M190`/`M109`/`PRINT_START …`) and it does not
reach the dump. `src/qt/assets/base-config.json:542,642` is where the COREONE text
lives, and `SettingsModel::seedFromProfile()` is supposed to have it replaced by the
resolved preset before anything slices — for these two keys it does not.
**Consequence: no file the app writes today is safe to print on this machine**
(Klipper answers `Unknown command:M862`/`M555`, and a 250×220 core-one start on a
350 bed). Workaround that works now: slice with HFW's own shipped profile,
`hfw-cli MODEL.stl --profile profiles/voron_klipper.cfg --gcode OUT.gcode`, which
writes `PRINT_START BED=… EXTRUDER=…` / `PRINT_END` and verifies PASS.

**1. Saving a foreign 3MF changes its toolpath.** Reproducible, documented at
`docs/known-issues.md`: `--export-project` on a `.3mf` prints *the project slices
differently from the plate it came from* — same layers, moves and filament total,
different digest — and the reopened plate carries one more per-object override than
the file did. Does not reproduce from an STL, which is why no gate saw it. **Still
open.**

**2. Export invents a layer-height profile.** A project written from a file that
carried none comes back with `Metadata/Slic3r_PE_layer_heights_profile.txt` (1–6
bands), which combined with organic supports makes the file refuse to slice.
**Still open**, and the writer is where it happens.

**3. Sequential printing without clearance validation.** Confirmed by reading the
code: `print_sequence`/`complete_objects` reach the engine as settings
(`PresetImport.cpp:233`) and nothing in `src/qt/src` checks gantry clearance. HFW does
plan per-object stacks, so the plate *will* be sliced sequentially with no collision
check. Printer-safety item.

**4. Patch documentation was wrong — fixed today.** `THIRD-PARTY.md` described one
patch ("two `add_subdirectory` lines, and nothing else"); there are six, +352/−16
lines across 45 file-touches. It now has a table of all six, what each changes, which
feature depends on it, and the three capabilities a replacement engine must carry:
the bottom-surface role, per-role fan speeds, and the in-layer extrusion channel.
`AGENTS.md` carried the same error and is corrected.

**5. HFW's verifier is honest only about what it reads.** Confirmed by reading
`crates/gcode/src/verify.rs`: unknown command codes are skipped, and only codes in
`is_numeric_command` (`G0 G1 G2 G3 G28 G90 G91 G92 M82 M83 M104 M106 M109 M140 …`)
are checked for readable values. A PASS therefore means *nothing this verifier knows
about is wrong*, which is not a firmware-level certification. It should say so in its
report line, and it does not yet.

**6. The 3MF importer is a hand-written XML scanner.** Confirmed: `crates/mesh/src/
threemf.rs` (654 lines) scans tags and attributes with string matching, and
`read_to_string` pulls each entry out of the zip with no size budget. Valid but
unusual XML (namespace prefixes, escaped attributes, nested components outside the
tested shapes) and hostile archives are both untested territory.

**7. Custom machine preset discovery** — *not re-verified this session.* The handoff
reports a machine saved with Save As that then does not appear in the picker. Reproduce
before fixing: create → save → restart → select. Treat as unconfirmed until then.

## Confirmed risks, not bugs

- **Curved surfaces get 12–16% less material at low infill than Orca/Prusa**, because
  more of it is classified as wall. One torus was printed and looked right; that is
  evidence for the classification, not proof for domes, cones and thin curved walls.
  The regression corpus needs those shapes before anyone calls the difference an
  improvement.
- **The distance field has a hard ceiling** (`MAX_FIELD_CELLS = 32_000_000`, refuses
  with `TooLarge`). Keep it. A tiled implementation is the real fix and is not
  started; do not raise the limit to accept bigger models.
- **CI is static checks only** (`.github/workflows/check.yml` runs `tools/check
  --static`). The real gate is local and needs a built engine plus a display.
- **Hardware coverage is one machine and one firmware.** Everything else is
  implemented-but-unproven and must be reported that way.
- **HFW's documentation claimed it has no third-party crates**; it uses `zip` and
  `regex`. Corrected in `DESIGN.md` today.

## Five next tasks

1. **Print the 3DBenchy through HFW.** It is sliced and verified
   (`/tmp/benchy.gcode`). This is the gate the whole engine plan stands on: if the
   G-code prints well, the migration has a foundation; if not, nothing else matters.
2. **Fix the 3MF round-trip**, starting with the extra per-object override — that is
   the visible symptom and the likeliest cause. Add the export-selftest assertion on
   the digest so it cannot regress silently.
3. **Stop the writer inventing layer-height profiles.** No profile, empty profile and
   populated profile must stay three different states.
4. **Refuse unvalidated sequential arrangements.** Compute the gantry envelope
   (height, X/Y travel, toolchanger offsets) and refuse rather than warn.
5. **Triage the 119 engine names with no phase yet** in `engine-boundary.md`, so the
   migration plan's estimates become certainties.

## Decisions to settle before HFW integration

| Decision | Options | Recommendation |
|---|---|---|
| Boundary type | C ABI (`crates/capi`) vs subprocess vs C++/Rust FFI generator | **C ABI**, with the subprocess kept as the CLI path for testing |
| Ownership across the boundary | engine owns plate and returns immutable results vs application owns and engine borrows | **Engine owns, application holds handles**; borrowed mutable state across FFI is the bug generator |
| Cancellation and progress | callback into C++ vs polling a job struct | **Job struct + poll**, so no Rust code ever runs on a Qt thread |
| Determinism | hash of output pinned in a test on both sides | **Yes** — a plate that slices differently between builds must fail loudly |
| What ships without the engine | paint, text, cut, hollow, STEP, SLA, nesting | **Out of scope**, written down in `rust-engine-plan.md`, not implied |

## Divergence from the handoff

The handoff ranks protecting user projects (the 3MF round-trip) first. That is right
for a project with users, and this project has none yet — the only person who has
opened a foreign 3MF is its author, and there is a workaround (do not re-save a
foreign project). Whereas the engine has never printed through the app. So the order
above puts the print first and the round-trip immediately second; if you disagree, the
round-trip moves to first and costs a day either way, because both are in front of
everything else.
